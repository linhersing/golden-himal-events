# Golden Himal Voice — UX 設計最高原則（鶴昇 2026年11月2日確認）

> **簡單、清楚、一眼就懂。寧可多幾個短頁，也絕不把功能塞成讓人找不到按鈕的長頁。**

此檔是本專案所有 GPT/Gemini/工程師/PR 的設計驗收依據。介面設計不可因為「功能已寫好」就強迫使用者理解工程流程。

## 2026年11月4日｜前台與後台分流的長期安全守則

- 公開首頁只供「我要報名／會員登入／最新公告」；訪客不顯示後台捷徑。這是**減少干擾與誤點**，不是把頁面藏起來就認證成功。
- 測試期保留完全不變的 `/backoffice.html` 私人直達 URL（交付專案管理者），不要破壞 GitHub 及其他測試入口；正式受保護管理網域／路徑完成前，不得刪除使用中的測試通道。
- **隱藏URL不等於資安**：未授權者即使直接猜到後台 URL，`/api/e2e/organizer-queue`、`/api/e2e/reviewer-queue`、評分／管理 API 都要由伺服器驗證 session 與角色；`/api/staging/management/*` 另須 Cloudflare Access 及管理員白名單，不能相信瀏覽器的角色參數。
- 正式發布前，要套用 Cloudflare Zero Trust Access 的管理端專用範圍，含所有相同後台的自訂網域、`workers.dev`替代入口及敏感管理 API。**不可錯套到整個對外報名 Worker**，否則歌手首頁也會被要求工作人員登入。Cloudflare 文件 https://developers.cloudflare.com/workers/configuration/cloudflare-access/ 。
- 工作人員後台未來為一個登入網址、伺服器分派主辦與評審權限，不代表兩種權限合成一種。由受邀名單、獨立身分及寄件網域驗證通過後才能完整實測，不可僅輸入Email就通過、不可關閉敏感頁驗證。
- 任何資安進度都需分成「公開連結已移除」「後端角色保護已查核」「Cloudflare Access 已部署」「受邀工作人員真實登入已驗收」四個不同狀態，不能只完成其一就宣稱100%安全。
- 交接工單：https://github.com/linhersing/golden-himal-events/issues/51 。每次程式變更、回復點、對照截圖及真實部署結果均記入 Drive 00_MASTER、00_AI_BRIDGE 和 03_網站更新與版本回復紀錄。

## 永久不變的產品架構

- **給參賽者的首頁**：只有三個主入口——「我要報名」「會員登入」「最新公告」。精美而簡潔，首屏讓人知道下一步。
- **給參賽者的子頁**：一頁只做一個主要任務，例如登入／驗證、填寫資料與作品、查看個人專區、付款狀態。可以多頁，不能長頁堆疊。
- **工作人員後台**：另一個入口，主辦方與評審共用一個網址，伺服器驗證權限，依角色只顯示必要資訊。
- **工程測試**：不要成為參賽者看得到的主要入口。不得將測試角色碼／D1／API／PR 作為公眾頁面的主文案。
- **資料真相**：所有持久資料須由受控後端儲存與讀回，前台不得假裝成功。尤其**未經正式支付系統確認入帳，不得標成「正式報名成功」**；模擬付款只能供內部驗收。

## 每次修改 UI 都必須核對

1. **目標明確**：五秒內看得懂「這頁要做什麼」，每頁一個主要 CTA。
2. **少即是多**：能移到下一頁的說明、選項、工程細節就移走；嚴禁為展示功能而堆疊選單。
3. **手機優先**：320/375/390px 無橫向捲動，主要 CTA 在手機第一屏優先露出，觸控目標至少約 44px。
4. **跨頁一致**：首頁、登入、會員專區、公告及後台維持同一品牌視覺；參賽者流程支援繁中／英文／尼泊爾文且不混雜。
5. **看得到結果**：提交後顯示真實可核對的狀態、報名編號、下一步；回來登入可找到原資料，按規則編輯／刪除。
6. **不誤導**：寄信未開通就說明無法驗證；金流未開通顯示「待付款／尚未開放」，不可使用假成功。
7. **角色與隱私**：會員只能看本人的資料；評審只能操作授權評分；主辦方才能讀管理資料。
8. **真實驗收**：在 PR 說明附電腦版、手機版 320/375px 檢查與 API／D1 實際驗證證據。GitHub CI PASS 不等於 Workers 線上已更新。
9. **完整留檔**：每次操作前後寫 Google Drive 的 00_MASTER 和 00_AI_BRIDGE；測試造成的 GitHub Email 在完成歸檔後逐封核對清理。

## 2026年11月4日更正｜三語切換不可刪除（PR #49）

- 首頁、會員註冊／Email 登入、我的參賽專區、編輯、模擬付款及最新消息必須保留「EN／नेपाली／中文」三種語言的可見切換工具；各頁共享同一語言偏好，跨頁、重新整理及登入後皆不得自動變回英文。
- 英文為尼泊爾對外的預設設計優先語言，尼泊爾文要完整可用，繁體中文供台灣測試與王老師檢查；「英文優先」**絕不是刪除中文與尼泊爾語的授權**。Email OTP 暫採穩定的英文簡短格式，不等於網站只能英文。
- 已存在 D1 報名資料的會員不重複出現大幅「新增報名表／報名簡章」；登入後先展示本人的報名卡、編輯、作品和模擬付款狀態。真正的第二梯次補報流程應另訂規範，不默默新增多筆。
- 最新公告可展開閱讀，但應使用專業、極簡、留白與資訊層次分明的列表設計，不要四個厚重米色方塊。V2資訊只能標為規劃，未核定不得假稱官方公告。
- 所有翻譯、改版必須做中英尼三語切換、手機寬度、完成畫面及 returning-member case 的自動化測試與截圖；保留安全邊界與原始URL不變。
- Codex PR #48 review 發現 community 組別 application.reset 後勾選必填狀態未同步，已在後續修復中補 toggle()；不能因收到 GitHub 通知後「CI 都過了」就忽略有實質內容的審查意見。

## 2026年11月4日新增｜尼泊爾參賽者優先、截圖與交接不可省略

- **語言**：報名介面英文為主，重要 CTA 可加極短尼泊爾語輔助；中文以內部測試為主，不應把三套完整語言堆進同一封 Email。OTP 測試信保持英文短訊、只顯示六位碼時效與測試標註。
- **不要藏 CTA**：登入後「Start a new application」必須是可見大按鈕，可點擊、可鍵盤聚焦，按下後直接展開表單並移動焦點；不可只靠小三角形。
- **V2 規章來源**：核對 Alan V2 規章、2026年10月30日之規章摘錄與前線正式通知。省份只按 Bagmati/Gandaki；組別為單選；只顯示該組別適用的資格聲明。現階段 Demo 連續60–90秒且不得修音剪接。僅靠影片 URL 無法可靠驗證時長，必須誠實註明人工核查，不能宣稱已自動拒絕超時影片。
- **測試付款完成**：僅在受邀測試環境內，當 D1 讀回 simulated_paid 才顯示「TEST REGISTRATION COMPLETE / NO CHARGE / NOT OFFICIAL」。此為內部模擬流程完成，絕不可寫成正式報名或真實已收款。
- **刪除安全**：刪除未付款記錄必須二次確認，清楚說明不可回復。受控測試使用虛構記錄，不碰使用者既有成果。
- **照片與個資**：肖像/證件屬高敏資料；沒有安全R2綁定、存取權限、清除政策與前線核定前，不能假設照片已儲存或開放不受控外部相簿；以可選、單張、壓縮與最小蒐集為後續設計原則。
- **每一批修改要留圖**：按鈕、表單、付款畫面、最新公告及手機頁變更均保留**修改前及修改後**實際 UI 截圖。截圖須註明桌機/手機、真實部署/本地測試、真人資料/虛構資料的差別；不包含密鑰、OTP、姓名等敏感資訊。若尚未部署，只能標記 PR/CI 預覽截圖，不得充作正式上線驗收。
- **每次換對話不重問**：開工前讀 Google Drive 00_MASTER、00_AI_BRIDGE 最新置頂及本檔；提交 PR 記錄檔案、commit、CI、前後畫面、部署狀態、回復點、尚缺資料到 03_網站更新與版本回復紀錄。任何只完成一半的工作都不能寫成 100% 完成。

## 下一階段設計順序（先可用，才求更多）

### Phase 2A — 歌手的報名到回訪動線（最高優先）

- **登入／註冊**：同一入口輸入 Email → 驗證；無法寄信時如實顯示，不能偽造登入。
- **填寫報名**：個人／組別／曲目與作品連結，依操作拆成短步驟；每步有返回與下一步。
- **我的專區**：登入後直接看到自己的作品、報名編號、付款狀態和「修改作品」；依流程允許刪除未付款、未審核申請。
- **付款**：另設獨立步驟；正式金流未接時標示待付款，不放在公眾頁的模擬繳費成功流程。

### Phase 2B — 後台精簡

- 主辦方首頁先顯示**正式已付款報名數**（未接金流時為 0），再到名冊及作品審核子頁。
- 評審登入同一後台網址，但只到自己的「待評作品 → 評分 → 已評結果」。
- 48 小時補件、排名及晉級流程安排在角色子頁，不要全部顯示於後台總覽。

**阻擋條件**：若 PR 把測試實驗室、技術術語、表單與評分混回參賽者首頁，或讓假付款變真成功，即使自動測試綠燈仍不應合併。
