# Golden Himal Voice — UX 設計最高原則（鶴昇 2026年11月2日確認）

> **簡單、清楚、一眼就懂。寧可多幾個短頁，也絕不把功能塞成讓人找不到按鈕的長頁。**

此檔是本專案所有 GPT/Gemini/工程師/PR 的設計驗收依據。介面設計不可因為「功能已寫好」就強迫使用者理解工程流程。

## 永久不變的產品架構

- **給參賽者的首頁**：只有三個主入口——「我要報名」「會員登入」「最新公告」。精美而簡潔，首屏讓人知道下一步。
- **給參賽者的子頁**：一頁只做一個主要任務，例如登入／驗證、填寫資料與作品、查看個人專區、付款狀態。可以多頁，不能長頁堆疊。
- **工作人員後台**：另一個入口，主辦方與評審共用一個網址，伺服器驗證權限，依角色只顯示必要資訊。
- **工程測試**：不要成為參賽者看得到的主要入口。不得將測試角色碼／D1／API／PR 作為公眾頁面的主文案。
- **資料真相**：所有持久資料須由受控後端儲存與讀回，前台不得假裝成功。尤其**未經正式支付系統確認入帳，不得標成「正式報名成功」**；模擬付款只能供內部驗收。

## 每次修改 UI 都必須核對

1. **目標明確**：五秒內看得懂「這頁要做什麼」，每頁一個主要 CTA。
2. **少即是多**：能移到下一頁的說明、選項、工程細節就移走；嚴禁為展示功能而堆疊選單。
3. **手機優先**：320/375/390px 無橫向捲動，主要 CTA 在手機第一屏優先露出，觸控目標至少約 44px。
4. **跨頁一致**：首頁、登入、會員專區、公告及後台維持同一品牌視覺；參賽者流程支援繁中／英文／尼泊爾文且不混雜。
5. **看得到結果**：提交後顯示真實可核對的狀態、報名編號、下一步；回來登入可找到原資料，按規則編輯／刪除。
6. **不誤導**：寄信未開通就說明無法驗證；金流未開通顯示「待付款／尚未開放」，不可使用假成功。
7. **角色與隱私**：會員只能看本人的資料；評審只能操作授權評分；主辦方才能讀管理資料。
8. **真實驗收**：在 PR 說明附電腦版、手機版 320/375px 檢查與 API／D1 實際驗證證據。GitHub CI PASS 不等於 Workers 線上已更新。
9. **完整留檔**：每次操作前後寫 Google Drive 的 00_MASTER 和 00_AI_BRIDGE；測試造成的 GitHub Email 在完成歸檔後逐封核對清理。

## 下一階段設計順序（先可用，才求更多）

### Phase 2A — 歌手的報名到回訪動線（最高優先）

- **登入／註冊**：同一入口輸入 Email → 驗證；無法寄信時如實顯示，不能偽造登入。
- **填寫報名**：個人／組別／曲目與作品連結，依操作拆成短步驟；每步有返回與下一步。
- **我的專區**：登入後直接看到自己的作品、報名編號、付款狀態和「修改作品」；依流程允許刪除未付款、未審核申請。
- **付款**：另設獨立步驟；正式金流未接時標示待付款，不放在公眾頁的模擬繳費成功流程。

### Phase 2B — 後台精簡

- 主辦方首頁先顯示**正式已付款報名數**（未接金流時為 0），再到名冊及作品審核子頁。
- 評審登入同一後台網址，但只到自己的「待評作品 → 評分 → 已評結果」。
- 48 小時補件、排名及晉級流程安排在角色子頁，不要全部顯示於後台總覽。

**阻擋條件**：若 PR 把測試實驗室、技術術語、表單與評分混回參賽者首頁，或讓假付款變真成功，即使自動測試綠燈仍不應合併。
