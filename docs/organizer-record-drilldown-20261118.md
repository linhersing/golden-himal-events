# 主辦後台｜一位選手一個視窗、逐層查閱（2026年11月18日）

## 使用者現場需求
手機使用者不應在主辦後台持續往下捲動大量參賽者資料。舊版按「查看受控報名聯絡資料」的三角箭頭後，會把很多聯絡與作品資訊直接加進原本的長頁；即使一人五首 Demo 收合在 `<details>`，展開後仍過長。希望每個報名者獨立一列，點選後進入其專屬視窗，再逐項深入查看，不必把所有人/所有歌/所有聯絡資料同時展示。

## 本次已改的前端資訊架構

```
主辦名冊：搜尋 + 一人／一個 application_id／一列
  └─ 點「查看資料」→ 選手專屬視窗（手機全屏，桌面置中）
       ├─ 歌曲與影片 → 五首作品短列表 → 選其中一首 → 單曲資訊/觀看連結
       ├─ 基本資料與照片 → 姓名(演出名)、編號、組別、賽程、地區、照片
       ├─ 受控報名聯絡資料 → 權限隔離頁（目前未接私密查詢，不顯示個資）
       └─ 報名審核與補件 → 現有核准/48小時補件操作 + 確認提示
```

所有步驟使用**同一個**語義化 `<dialog>`，只替換單一內容區；避免彈窗堆疊導致Android返回/焦點混亂。每頁有「上一步」及「關閉」，Esc 可關閉，關閉後恢復原本選手按鈕焦點。電話、Email、真實姓名、住址與詳細聯絡資料不會預載至名冊 DOM。

## 原API與安全邊界

- `/api/e2e/organizer-queue` 現有主辦API已限制角色，回傳非私人名冊/影片等摘要，**尚無完整受控聯絡資料查詢API**。本PR不新增冒用的聯絡資料，也不直接從D1帶出私密欄位。
- 受控聯絡資料仍需先完成受邀主辦身分、按需的受控查詢、伺服器權限確認與查閱稽核後才能顯示。前端已預留獨立步驟，但尚未實現真實查詢。若前線要求進一步開通，必須另外設計最小授權的API，不能把原本所有私人欄位直接附加到 `organizer-queue`。
- 保留 `application_id`、所有歌曲連結與角色檢查、原本核准與補件 API。沒有更動D1資料或評分紀錄。
- 顯示的一列是「一筆報名」而非用名字合併多筆；同名不同ID不能混在一起。
